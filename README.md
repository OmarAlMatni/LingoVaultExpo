# LingoVault v2 (Expo / React Native)

A ground-up rebuild of LingoVault as a real Expo + React Native + TypeScript
Android app. The old React/Vite/Capacitor/Kuromoji project (`lingo_vault.zip`)
was used **only** as a functional/UI reference, per your instructions — no
code, dependencies, or architecture were carried over. There is no Capacitor,
no WebView, no Kuromoji, and no `.dat.gz` dictionary assets anywhere in this
project.

Everything below was actually built and, where it's possible to verify
without an Android SDK/emulator, actually tested — not just described. See
"What I could and couldn't verify" (section 13) for the honest boundary.

## 5. Tokenizer: TinySegmenter, and why (not Suzume, not Kuromoji)

I checked Suzume first rather than assuming. It's real and more accurate
than TinySegmenter, but it ships as **C++ compiled to WebAssembly**
(`@libraz/suzume` on npm). Hermes, React Native's default JS engine, has no
WebAssembly runtime, and there's no published React Native binding for it.
Using it would mean writing a custom native module embedding the C++
library — a much bigger native commitment, and it reintroduces the exact
"binary blob asset" risk this rewrite exists to eliminate. I didn't want to
quietly swap one asset-loading problem for another.

TinySegmenter is a ~18KB pure-JS statistical model — no dictionary files,
no WASM, no native module. It's ordinary JS in the RN bundle, so the entire
bug class from v1 (WebView asset paths, `.dat.gz`, APK asset sync) simply
doesn't exist for it.

**Real, verified trade-offs** (I tested these, not theorized):
- No dictionary awareness → raw segmentation over-splits fixed expressions
  (`こんにちは` → `こん`/`にち`/`は`). Fixed via a dictionary-assisted
  greedy re-merge pass in `OfflineTranslationService` — after segmenting, it
  tries merging runs of 2–6 consecutive tokens and keeps the longest span
  that's an actual dictionary headword.
- No lemmatization → `TinySegmenterTokenizer.ts` layers a hand-written,
  deliberately limited conjugation-recognition table on top (ichidan/godan
  verbs, i-adjectives, する-verbs). It won't catch every irregular form.
  Genuinely less accurate than Kuromoji's IPAdic-based lemmatization — the
  trade-off for not shipping multi-megabyte dictionary files. Ambiguous
  godan endings (買った could be 買う/待つ/乗る) are resolved by returning
  candidates and letting the dictionary pick the one that actually exists,
  the same technique real lightweight taggers use.

`JapaneseTokenizer` is a plain interface specifically so this can be
swapped later without touching anything else — e.g. if a Suzume RN binding
appears, or if you want to invest in a full lattice-based tagger.

## 6. Offline dictionary

`assets/dictionary.db` is a bundled, **read-only SQLite file**, imported
into the app's private storage exactly once via expo-sqlite's documented
"import an existing database" mechanism:

```tsx
<SQLiteProvider databaseName="dictionary.db" assetSource={{ assetId: require('../assets/dictionary.db') }}>
```

After that first import it's a normal on-disk, indexed SQLite database —
fast lookups even at full JMdict scale (~190k entries), nothing fetched
over any network-shaped API (no `fetch('/dictionary.json')`, no WebView
asset routing at all). `metro.config.js` registers `.db` as a bundleable
asset extension, which is the one Metro-specific step this pattern needs.

`scripts/build-dictionary.js` converts JMdict_e's XML into this format. It
streams the file line-by-line (never loads the whole XML into memory),
extracts kanji/kana/gloss/part-of-speech, and writes to SQLite via Node
22's built-in `node:sqlite` module — a build-time-only tool, nothing it
uses ships in the app.

**Important**: the `data/JMdict_e` file in your uploaded reference project
was empty (0 bytes), so I could not build the real dictionary from it. I
ran the script anyway to prove the pipeline works, which is why
`assets/dictionary.db` currently has ~20 seed entries (enough to run the
app and your test plan) rather than the full ~190k JMdict entries. Get the
real file per `data/README.txt` and re-run `npm run build:dictionary` —
it's a drop-in replacement, nothing else changes.

## 7 & 8. PROCESS_TEXT and how the popup receives text

This is real native code, not a JS simulation — added by an Expo config
plugin (`plugins/withProcessTextPopup.js`) at `expo prebuild` time, so it
regenerates correctly every time and isn't lost by `--clean`.

**What the plugin does**, verified by running its manifest/styles logic
against a synthetic Android project (I don't have an Android SDK in this
environment to run a full `expo prebuild`, so this is the level of
verification that was possible — see section 13):

1. Writes `android/app/src/main/java/com/lingovault/app/TranslatePopupActivity.kt`
2. Registers it in `AndroidManifest.xml` with the real
   `ACTION_PROCESS_TEXT` / `CATEGORY_DEFAULT` / `text/plain` intent-filter
3. Adds a `Theme.Popup` style (floating, no title, dimmed background) and
   applies it to that Activity only
4. **`MainActivity` is untouched** — it stays the plain launcher, exactly
   per your instruction ("PROCESS_TEXT should launch the dedicated
   translation popup", not MainActivity).

**How selected text reaches the popup UI:**
`TranslatePopupActivity.kt` reads `Intent.EXTRA_PROCESS_TEXT`, then — before
calling `super.onCreate()` — rewrites its own held Intent into
`lingovault://popup?text=<encoded>` and lets Expo Router's built-in deep
linking resolve that to `app/popup.tsx`, with `text` as a route param
(`useLocalSearchParams()`). This reuses Expo Router's own tested linking
machinery instead of a custom native bridge. The popup Activity hosts the
**same** registered JS root component (`"main"`, verified against Expo's
actual generated template) as MainActivity — there is no second app bundle,
no second translation engine. `app/popup.tsx` calls the exact same
`useAppServices().translationService` the Translate tab uses.

**Save-from-popup**: `SaveToListRow` (shared component) writes to the same
`VocabularyStorage`/SQLite database the Lists tab reads from — a word saved
in the popup shows up in Lists with no sync step, because it's literally
the same database file.

## 9. Local vocabulary storage

`VocabularyStorage.ts` — a second, **writable** SQLite database
(`vocabulary.db`, separate from the bundled read-only `dictionary.db`),
created fresh on-device on first run. Two tables: `lists` and `items`
(foreign-keyed to a list, storing japanese/kana/romaji/meanings/pos/tags/
notes/favorite/created_at). Survives app restart and phone restart because
that's just what an on-disk SQLite file does — no extra persistence layer
needed.

## 10. Running the project

```bash
npm install
npm run build:dictionary     # generates assets/dictionary.db (seed data by default)
npx expo start
```

Scan the QR code with Expo Go for the fastest iteration loop on the parts
that don't need PROCESS_TEXT (tokenizer, dictionary, Translate screen,
Lists, Settings). **PROCESS_TEXT will not work in Expo Go** — it needs the
custom native Activity, which only exists in a prebuilt/dev-client or
release build (see below).

## 11. Building an Android APK (with PROCESS_TEXT)

```bash
npm install
npm run build:dictionary          # or drop in the full JMdict-built db first
npx expo prebuild -p android      # generates android/, runs the config plugin
cd android
./gradlew assembleDebug
```

Install and test:
```bash
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

Verify PROCESS_TEXT is really wired up before you rely on it: open the APK
in Android Studio's APK Analyzer and check `AndroidManifest.xml` for
`TranslatePopupActivity`, or just test on-device — select Japanese text in
Chrome or any text field, "LingoVault" should appear in the text-selection
menu, and tapping it should open a small card, not the full app.

## 12. Native Android steps required

None beyond the standard `expo prebuild` + Gradle build above — the plugin
handles the manifest/theme/Activity generation automatically. You do not
need to hand-edit anything in `android/`.

## 13. Limitations (read this before assuming something works)

- **Tokenizer accuracy** is meaningfully lower than Kuromoji's for anything
  outside common conjugation patterns and dictionary-known fixed
  expressions. It's a dictionary-based word-by-word analyzer, not fluent
  machine translation — matches your own spec, but worth restating plainly.
- **Kanji readings for words not in the dictionary** can't be derived —
  there's no algorithmic kanji→kana conversion without a reading lookup, so
  unknown kanji words show `found: false` rather than a guessed reading.
- **The bundled dictionary is currently the small seed set** (~20 entries),
  not full JMdict, because your reference project's JMdict_e file was
  empty. The pipeline is real and tested; the data isn't populated yet.
- **I could not run `expo prebuild` or a Gradle build myself** — this
  sandbox has no Android SDK/JDK/Expo CLI network access. The config
  plugin's manifest/styles logic was verified by running it directly
  against a synthetic Android project with the real installed
  `@expo/config-plugins` package; the Kotlin Activity source was checked
  against Expo's real, current generated `MainActivity.kt` (fetched from
  GitHub) and a specific Kotlin/Android interop question (whether
  `intent.data = uri` works when `setData()` returns `Intent` rather than
  `Unit`) was independently verified rather than assumed. That's a solid
  level of confidence, but it is not the same as "I ran the build and it
  produced a working APK" — you'll need to do that build yourself, and
  it's possible something surfaces that only shows up at actual compile
  time.
- **No app icon/splash configured** — I removed those fields from
  `app.json` rather than reference image files that don't exist in this
  project; Expo will use its own placeholder icon until you add real ones.
